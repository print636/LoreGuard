# 角色 OOC 跨剧情开发检查点（2026-09-23）

本检查点使用新增的原创 [潮镜站 DEV 挑战集](../data/character-ooc-challenge-v1/README.md)，经本地 HTTP API、PostgreSQL/Celery 和账户级 OpenAI-compatible Provider 跑完整角色设定候选确认与新稿审查流程。请求配置中的模型别名是 `deepseek-v4-pro`；别名不证明上游实际权重。样本由开发者编写并在本轮调试中可见，**不是盲测、开放文本质量或生产可用性结论**。

## 预先关注的三种情况

1. 南枝：在两个独立时段主动与陌生人长谈，正式核心性格与新稿相反，材料中没有已发生的成长或任务桥梁；期望带基线和两条新稿证据的冲突。
2. 郁礼：同样出现更主动的公开交流，但已发布章节记录连续八周训练；不能报确定冲突，只有在观察和因果证据都被抽取、绑定后才能说明“已解释”。
3. 岑烛：警报发生时仅一次厉声打断队友，随后恢复平时方式；不能据单次紧急行为判定稳定人格改变。

Oracle 只在模型输出后用于评分，不进入上传正文、模型 Prompt 或账户配置。首次 DEV 探针暴露了岑烛标注的比较轴方向歧义；现以 `interruption_restraint/positive` 或 `interruption_behavior/negative` **成对**接受，不接受交叉组合。该修正发生在开发集观察之后，所以本集从未具有 holdout 资格。

## 真实运行结果

严格首轮在正式背景阶段停下：3/3 分块处理完成并生成三名目标角色的正式设定候选，但整体为 `partial`；真正的记录拒绝原因包括 `key_object_support` 7。`source_formal` 2 与 `source_history` 1 只是来源类型计数，不是拒绝原因。安全门没有把部分覆盖写成完整通过。

随后使用仅限此 DEV 集的 `--diagnostic-continue-partial-baseline` 继续观察。一次越过候选选择前，因上述标注方向歧义停下；修正成对 Oracle 后的一次完整诊断结果如下：

| 项目 | 结果 |
| --- | --- |
| 正式背景 | 运行完成；3/3 目标候选人工确认，但角色阶段 `partial`，不是完整覆盖 |
| 待审新稿 | 运行完成；角色阶段 `partial`，仅有 2 条新稿观察；定向补抽出现 Token 预算不足 |

原始脱敏运行 JSON 留在 Git 忽略的 `artifacts/character-ooc-diagnostic-3-20260923.json`，未提交故事请求、模型原始回复或密钥。运行器现将“至少三轮独立完整流程”的 claim 与实际门槛绑定，单轮不会再误写为 `true`；新产物也采用只创建、不覆盖语义。这两项运行器修正发生在上述诊断产物之后，不改变当次模型观察或失败结论。

## 判断边界与后续定位

当前安全诊断表明：被拒绝的记录涉及原文对象或角色绑定，且补抽受阶段预算约束。新稿第一条南枝行为使用承接上一行的代词；现有抽取器/定向补抽要求证据内明确点名角色，因此**这是一个值得隔离实验的可能漏报因素**，不能仅凭本次脱敏产物断言它是唯一原因。下一步应在 DEV 对照中分别检查显式角色名、多行连续证据、代词归属和预算耗尽，记录每个阶段的覆盖差异；任何归属扩展必须维持原文证据、唯一先行词与跨角色/分支拒绝。随后另建未见世界观评估，不能把本集反复调绿后称为独立验证。

本次不放宽 `key_object`、角色归属或证据门，也不因为没有可见问题就判定新稿已通过。

## 后续迭代与复测（同日）

为检验上述漏报因素，服务端新增了一个**仅适用于待审新稿**的相邻指代证据路径：前一句须明确锁定单一角色，后一句只能以单数“她/他”承接；两句必须同段且连续，记录的 `statement` 必须是后句逐字将该代词替换为角色名。多角色、引语、条件/分支、空行及概括性改写仍拒绝。定向候选核验可以展示这两行，但模型返回的范围仍需服务器重新校验。另将方向写进 `trait_key` 的明确英语词（例如 `_avoidance`）作为可恢复的记录错误，而非静默转换语义轴；重试证据锚点过多或预算不足时也明确降级，不删减锚点以求通过。

同时，在首次调用新世界观前固定了原创 [雾岬信标节迁移集](../data/character-ooc-transfer-v1/README.md)及其候选比较轴、预期结论与证据 Oracle。首次真实模型运行在候选确认阶段失败：目标角色的模型键名落在冻结允许项之外，另两人的键名还出现了方向词。这是模型输出及精确评测器的共同边界，不能事后扩写 Oracle 冒充盲测成功。加入通用中性键校验后的复测仍未进入新稿，因为一名目标角色没有留下可唯一确认的正式设定候选。

为了观察后续链路，另加 `--diagnostic-review-source-anchored-candidates`：仅允许一轮 OOC DEV 运行，在角色、维度、设定来源行和原文值均唯一匹配时模拟用户确认；它**不检查**候选 `trait_key/polarity/stability`，因此报告明确标记诊断模式并强制 `passed=false`，绝不能用来替代严格 Oracle。搭配 `--diagnostic-continue-partial-baseline` 的旧 DEV 集实测进入新稿：正式阶段完整，确认 3 个候选；新稿阶段仍是 `partial`，只有 3 条观察。南枝仅绑定 1 条行为而未报预期冲突；郁礼有 2 条行为与已发布训练桥梁并被解释；岑烛未绑定到行为，不能把无误报说成正确判断。这次模型调用仍**没有**验证两行代词正例：单元与 Mock 测试证明服务器会接纳完全符合证据契约的记录，真实模型尚未稳定产出该记录。

上述运行使用本地 Docker 容器的 100000 阶段 Token 测试上限，**产品默认仍为 60000**；真实调用的模型别名不证明上游实际权重。脱敏原始结果分别保存在 Git 忽略的 `artifacts/character-ooc-transfer-frozen-first-20260923.json`、`artifacts/character-ooc-transfer-diagnostic-neutral-2-20260923.json` 和 `artifacts/character-ooc-dev-diagnostic-neutral-2-20260923.json`。这一轮提升了证据绑定与排障能力，但 OOC 质量验收仍未通过，也没有开放文本泛化结论。

作为回归对照，同一新构建、同一 100000 阶段上限的旧原创 Demo 又做了 **3 次独立、严格候选确认的 HTTP 全流程**：三次正式设定和新稿阶段均为 `completed`，每次均显示预先标注的 2 个问题、完成全部 5 个案例契约，所有严格门槛 `passed=true`。脱敏结果为 `artifacts/character-demo-neutral-three-trials-20260923.json`。这是对**已知开发者可见 Demo** 的重复性证据；它与新 OOC 迁移集的失败并存，不能拿 Demo 通过外推“新角色/新世界观也可靠”，也不能把本地调高的测试预算当成默认体验或成本承诺。
