# 作者轴方向对齐 RFC（最小安全增量已实现）

状态：0018 最小安全增量已实现；下文保留原设计与验收边界。旧运行和冻结评测结果不改写；PostgreSQL 迁移/并发与跨故事真实模型质量尚需独立验收。目标是让“模型提出的特征方向”和“作者批准的比较轴方向”有显式、可审核的对应关系，而非凭否定词、候选标签或同一来源行猜测。

## 问题与现有边界

`character-axis-challenge-v2` DEV 的 S4、S5 目标分句已有独立的精确证据绑定候选，但候选方向为 `positive`，冻结计划要求 `negative`，严格选择器因而没有唯一命中。两个目标所在行的前半段另有正向的抽象性格主张；不能把整行、所有候选或看到“不会”的分句一概翻成负向。对“尊重签名自主／不冒用签名”而言，`signature_integrity + positive` 与“是否冒用签名 + negative”可以表达同一边界，方向相反来自**轴的正向命题不同**。现有快照未保存模型原始响应，不能断言模型原始字节或语义复核单独犯错。原冻结计划、oracle 和此前 3/5、4/5 等严格结果保持原样；新增实验须另行报告，不追认旧成绩。

当前 `CharacterTraitCandidateRow`、`CharacterTraitReviewRow` 只保存候选原 `polarity` 与 `approved_axis_id/version`（`app/db.py`）；确认 API 验证轴的项目、类型和版本，却未保存“候选方向相对作者轴”的映射（`app/main.py` 的 `CharacterTraitDecisionIn` 与候选决定处理）。`candidate_snapshot_payload` 和服务层冻结原方向并附上轴 ID/定义（`app/character_traits.py`、`app/service.py`），`ConfirmedTraitSnapshot` 也只有单一 `polarity`（`app/character_drift.py`）。草稿定向召回按该值直接取反，同轴提示的歧义判断亦直接比较它（`app/character_consistency_stage.py` 的 `_safe_server_context`）；审核同轴冲突同样比较候选原方向。现有前端只让作者选轴，未让其核对方向对应（`frontend/src/features/characters/CandidateReview.tsx`、`CharacterWorkspace.tsx`）。

## 审核契约

1. 作者轴须附有一条明确、可判定“成立／不成立”的**正向命题**，例如“角色未经授权冒用搭档签名确认换班”。这不是模型凭空生成的事实，也不代表人物一定这样做；它只定义比较方向。现有 v1 轴只有名称与定义，不能从名称自动推导正向命题。建议新增不可变的轴正向命题记录，引用既有轴 ID/版本并包含命题正文、哈希、版本、创建者；既有轴由作者显式补定义，新建轴同时创建。不可静默回填旧轴。
2. 作者确认某个已验证目标候选并绑定轴时，需看到目标分句、必要主体／标签承接、候选原 `trait_key/polarity`、轴定义和正向命题，再选择 `same`（候选原方向等于轴方向）、`opposite`（相反）或 `uncertain`。`uncertain` 不得建立可用于方向性 OOC 的轴绑定；可以保留待审或驳回，不能为了通过评测强行选方向。AI 可提出建议和引用，但不是审核权威；服务端不得接受模型自行签发映射。
3. 永远保留候选原 `polarity`、`trait_key`、证据及指纹。另存作者审核的 `axis_alignment` 和由原方向计算的 `axis_polarity`，并约束两者一致：`same` 保持原正负，`opposite` 对调；例如原 `signature_integrity + positive` 对“会冒用签名”的正向命题为 `opposite`，其轴方向是 `negative`。原方向只相对于原 `trait_key`；轴方向只相对于轴正向命题。原方向为 `neutral/unclear` 时，不允许计算有方向的 `axis_polarity`。同轴去重、冲突、覆盖与歧义比较使用已验证的轴方向；以原标签发起的草稿定向抽取仍使用原方向及其反向，二者不得混用。
4. 旧的“已绑定作者轴但无方向映射”记录标为 `legacy_unverified`：不默认 `same`，不自动重写旧确认或旧快照，不以该轴产生方向性结论。新运行应显示材料覆盖不足／需作者补认；补认走独立的显式审核操作、追加审计、乐观锁与幂等，只影响之后创建的运行。旧运行和报告保持冻结。

## 最小落地里程碑

1. **契约与存储。** 冻结正反、跨分句、相反命名轴和不确定样本；新增轴正向命题记录及候选／审核方向映射列（下一增量迁移，不改旧行）。PostgreSQL 约束校验项目、版本、`same/opposite` 与 `positive/negative` 成对关系；SQLite 升级库避免无差别重建旧候选表导致约束丢失，使用受测的附加校验与应用层 fail-closed。迁移的升降级、旧行与并发写入需实测。
2. **作者操作与审计。** 创建或补认轴正向命题，以及确认候选时提供轴命题版本、`same/opposite/uncertain` 和当前候选修订；服务端核验当前来源、精确证据绑定、工作区／项目归属、CSRF、轴版本、幂等重放、竞争更新与追加审核记录。旧已确认行提供单独补认入口，不伪造一次新的模型抽取或改写原确认。前端显示两套方向的含义、证据与“不确定”出口，提交前要求作者明确选择，错误时保留输入并提示刷新。
3. **运行时隔离。** 新建运行的版本化快照及其哈希冻结原方向、轴命题身份／哈希、映射和轴方向；旧快照原样读取。草稿召回沿原标签使用原方向，批准轴层面的同轴判断使用轴方向；映射缺失、版本／哈希不合或方向自相矛盾均弃权并记录覆盖不足，不能退回原始极性冒充轴极性。分两个提交开发可以，但上述安全门槛和前端可补认路径必须一起通过后才开启方向性结论。
4. **验证。** 单元／API／集成回归覆盖：同一来源行的正向 A1 与负向 A2/A3 独立绑定、相反标签框架映射到同一作者轴、`uncertain` 和旧行弃权、无轴旧路径兼容、跨项目轴冒用、篡改映射／命题哈希、幂等／CAS／CSRF、撤销／替换、旧快照不可变、草稿目标原方向与轴方向不混淆。通过全量测试、数据库迁移测试及隔离端到端后，用未改动的冻结 DEV 材料做新方案的**独立、明确标记为作者定向审核**的真实模型复跑；人工步骤、未评案例、延迟和成本单列。原严格选择器成绩不改判，DEV 通过也不等于盲测或开放长篇质量达标。

拒绝方案：按“不会”字面翻转 S4/S5、把同线正向性格一起翻转、在评分脚本中忽略旧冻结方向、用模型自由标签猜测轴正向、把 `uncertain` 当 `same`、修改既有 oracle 或报告以制造通过率。
