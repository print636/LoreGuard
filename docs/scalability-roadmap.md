# 长篇剧情容量边界与扩展路线

更新时间：2026-09-01

## 当前真实边界

| 口径 | 当前值 | 含义 |
|---|---:|---|
| 已跑通长文 smoke | 24,418 字符 / 4 文档 | 生成型、无模型管线验收，不是人工准确率 |
| 单文件上传上限 | 10 MiB | 只表示可以存储，不表示可以可靠分析 |
| 模型分块 | 6,000 字符/块 | 保留全局证据行号，默认重叠 1 行 |
| 每文档模型块上限 | 24 | 表面覆盖上限约 144,000 字符；超过部分只保留基线覆盖 |
| 单次模型预算 | 20,000 Token | 实际通常早于块数上限停止；系统 Prompt 会随分块重复 |
| 关系图响应上限 | 500 节点 / 1,000 边 | 超限明确返回 warning |
| 版本差异输入上限 | 每版本 2,000,000 字符 / 20,000 行 | 只影响一次差异计算，不影响原文存储 |

当前建议把需要模型增强的一次项目分析控制在约 2 万至 5 万中文字符。更大的项目可以保存且全文基线仍会扫描，但不能据此宣称模型完成了全量语义审查。

## 为什么数据库不是首要瓶颈

原文当前保存在 SQLite/PostgreSQL `TEXT` 字段，抽取结果保存在带证据的 JSON 状态记录中。一千万中文字符的原始 UTF-8 文本大约只有数十 MB，关系数据库能够保存。真正限制来自：

1. 当前分析启动时把全部活动文档读入进程内存。
2. 未修改章节也会被重新解析和重新抽取。
3. 本地候选检索对抽取记录进行近似两两比较，记录数增长后接近二次复杂度。
4. 当前 JSON 状态记录不适合跨版本、跨篇章的增量查询。
5. 模型分块之间缺少长期状态摘要与隐含实体消歧。

文档历史列表已经只返回版本元数据，不再把所有历史版本正文一次性发送到浏览器；正文只在真正需要分析或比较时由服务端读取。

## 面向百万至千万字符的目标架构

### 第一阶段：增量抽取

- 为文档版本和分块保存 SHA-256 内容哈希、全局行号与抽取协议版本。
- 新运行只抽取新增或变化的块，未变化块复用已验证的状态记录。
- 保存每次运行实际使用的文档版本快照，保证结果可复现。
- 版本差异决定失效范围，并向前后扩展少量上下文块。

### 第二阶段：规范化状态库

- 建立实体、别名、事实、事件、知识获得、物品状态、规则及证据关系表。
- 所有状态带项目、篇章、来源版本、有效时间区间和抽取器版本。
- JSON 记录保留为审计输入，规范化表负责查询、去重和跨版本比较。

### 第三阶段：真正的混合检索

- 将原文块 embedding 写入 pgvector 并建立近似最近邻索引。
- 先按项目、实体、时间范围和篇章过滤，再做向量召回和重排。
- 以实体邻域查询替换全量记录两两比较；确定性规则只检查受修改影响的子图。
- 使用“世界规则摘要 → 篇章摘要 → 场景原文”的分层证据链，最终结论必须落回原文证据。

### 第四阶段：生产执行

- PostgreSQL 保存元数据、版本与规范化状态；对象存储保存大原文和导入包。
- Redis/Celery 按文档块并行执行，设置项目级并发、预算、取消和失败恢复。
- 初次导入允许离线建库数小时；日常单章修改目标是分钟级增量审查。

## 容量目标

- Alpha：2 万至 5 万字符，强调端到端可体验。
- 下一验收：10 万字符、20 至 50 文档，验证增量重跑和跨文档证据。
- 中期：100 万字符，要求真实 pgvector、规范化状态表和受影响子图检查。
- 长期：500 万至 2,000 万字符/项目，面向长线商业游戏量级；必须采用增量索引，不能做单次全量 Prompt。

这些是工程目标，不是当前完成事实。每一级都必须用人工标注的复杂长篇数据测量精确率、召回率、证据命中率、索引时间、增量延迟和成本后才能宣布达成。
