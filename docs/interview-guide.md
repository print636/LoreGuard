# LoreGuard 面试讲稿

## 1 分钟

LoreGuard 是给游戏编剧和叙事设计团队使用的一致性审查平台。它把原创世界观和章节文本解析成事实、事件、角色知识、物品状态与世界规则，再用确定性规则定位冲突。与普通聊天式审稿不同，每个问题都必须返回两侧原文证据、严重度、置信度和修订建议。当前 MVP 已打通 Markdown/TXT/JSON 导入与版本比较、五类检查、SSE、反馈、取消/重试、关系图和时间线。评测按用途分层：80 条显式指令只测规则接线，模板自然中文和 challenge-v2 测稳定回归，14 例原创多文档复杂集测困难反例。后者用真实模型跑了 3 轮，42/42 完整轮次的类别与严格证据评分均无 FP/FN、P95 约 85 秒；但它是开发者可见固定回归，我不会把它包装成人工盲测或生产准确率。

## 5 分钟结构

1. 痛点：长篇分支叙事的事实分散、角色认知随时间变化，纯向量 RAG 容易漏掉状态约束。
2. 数据流：文档版本 → 指令抽取 → 证据片段 → 混合检索 → 规则检查 → 问题报告 → 人工反馈。
3. 关键模型：`CanonicalFact`、`NarrativeEvent`、`KnowledgeAcquisition`、`EvidenceSpan`、`ConsistencyIssue`。
4. 权衡：关系表优先、SSE 单向流、确定性基线与 LLM 语义层解耦、反馈进入评测而非直接改规则。
5. 可靠性：输入大小限制、超时/429/非法 JSON 的 provider 边界、持久化事件、取消和重试、无 Key 降级。
6. 评测：按世界观拆分；报告精确率、召回率、证据定位率、延迟和成本，不用测试集做 Prompt 示例。

## 高频追问

- 当前有 RAG 吗？还没有检索内容回送模型的闭环。已有关键词、稳定 n-gram 与实体关系候选排序，不是真实 embedding；候选 trace 的类型兼容计数也不证明影响了裁决。Evidence RAG 已列入交付计划，不能提前写成完成经验。未来仍保留规则，因为向量相似不等于时序与状态冲突。
- 当前有 Agent 吗？还没有。模型目前执行固定结构化抽取，不自主选工具或补查；受限工具循环与 LangGraph 编排已规划但尚未实现，不能把多个固定步骤直接称为 Agent。
- 如何控制误报？权威来源优先级、时间范围、实体消歧、阈值校准和人工反馈分层统计。
- 如何控制成本？目前有逐分块 Token 门控、有限重试与熔断，已完成报告读取不再调用模型。跨运行缓存和共享原子访客额度尚未完成，不能把当前单实例每日检查当作生产配额保障。
- SSE 断线怎么办？事件落库，客户端携带最后事件编号重连；终态可用状态接口补查。
- 如何防 Prompt 注入？目前采用固定系统指令、文档数据隔离和结构化/证据校验，但这不等于完整的注入防护。当前没有工具执行能力；未来 Agent 需增加服务端绑定项目/版本、只读工具白名单、参数校验与恶意文档测试，不能仅靠 Prompt 约束。
