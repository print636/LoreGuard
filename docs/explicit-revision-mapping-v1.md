# 修订稿手动对应原文稿 V1

状态：实现、本地集中验收及五项 CI 完成（2026-11-11），本机备份、升级及安装以最终收据确认。

用户已确认：文件改名或由 Word 转为 Markdown 后，可以手动选择原文稿，将其保存为原文稿的新版本，保留原名称和版本链。

## 作者操作

逐文件导入和报告内修订上传均提供明确替换目标。选择目标后，上传前展示“本次上传文件 → 将更新的文稿及版本”，供作者核对。保存成功后显示平台保留的文稿名、新版本和本次上传文件名。

保存成功不等于新版本的资料身份已经确认。作者仍需核对它属于待审新稿还是其他材料、适用范围及身份；新版本尚未确认时，复检准备会明确提示，核对后再继续。显式文件对应不会替作者确认权威、发布状态或角色设定。

没有明确选中目标的上传继续沿用既有行为；不依据文件名相似度、内容相近或当前打开的报告猜测对应关系。一个上传文件明确对应一份原文稿；拆并章不自动配对。

## 名称与格式

- 解析使用实际上传文件的名称与格式，沿用既有 DOCX／Markdown／TXT／JSON 校验。
- 明确对应后，平台文稿名取原文稿名，版本沿原链递增。原名中的扩展名不表示本次上传文件的实际格式。
- 另有文稿恰好与上传文件同名时，不影响那份文稿；目标由作者明确选择决定。
- 导出目录中的名称表示平台文稿名；无法核对的历史上传文件名不得猜测或补写。

## 版本、收据与恢复

新上传必须验证目标属于当前账户的项目，且仍是作者选择时的有效版本。目标已被另一修订替代时要求重新核对，不悄悄选择最新版本。

每次操作冻结实际文件、目标、资料选项和幂等标识。服务端在同一事务中完成原版本替代、新版本、上下文及收据保存。响应核对既包含新文稿身份，也包含实际替换关系，不能只放宽文件名检查就接受成功。

成功操作的同一请求重放优先读取原收据，原目标已经被本次操作替代不妨碍重放。重放不创建新版本、重新激活旧稿或改变已确认资料。结果未知时保留原操作，只允许手动安全重试；更换文件或目标不能冒充同一重试。

现有上传收据增加一个可空的 `import_metadata` 字段，记录服务端构造的实际上传名、解析格式、明确目标版本及保留逻辑名；不新增表或复制原稿。旧空值保持原样。旧请求经原指纹匹配后可核对返回信息，但不能宣称历史元数据已经补存。

## 后端合同

仍使用 `POST /api/v1/projects/{project_id}/documents` 的 multipart 上传；文件沿用实际名称，`replace_document_id` 表达作者明确选中的原文稿。服务端在项目锁内核对有效目标与相邻版本，逻辑名仅取该目标，不按上传名覆盖另一份同名资料。

元数据结构版本为 `document-import-v1`，包含 `uploaded_filename`、`uploaded_format`、`logical_name`、`replaces_document_id` 和 `replaces_document_version`。响应的平台名称沿用 `name`，另外返回实际文件名、格式与替换目标字段；保存结构版本并不作为整包元数据直接返回。`upload_metadata_source` 区分 `stored_receipt`（已存收据）、`verified_request`（旧收据匹配当前请求后核对）和 `current_request`（当前请求）。这些字段供客户端核对，页面用普通名称、格式和版本表达，不展示内部标识。

迁移 `0026_document_import_metadata` 接续 `0025`，只为原上传收据增加可空 JSON 列。旧空值不回填；部署前沿仓库备份和升级流程处理。迁移与事务验证完成后补充结果，不把 ORM 新列可用等同于旧数据库已升级。

## 本批边界

这次改善修订回传，不自动发布、撤销角色确认、重写旧报告或调用模型。旧报告继续引用原版本；作者核对资料后自行启动复检。Word 格式是否保留取决于作者上传的原文件，平台原文和资料导出仍使用解析后的正文。

## 一次集中验收

后端以一批相关专项覆盖实际格式解析、明确目标名称与版本链、不同同名文稿隔离、过期目标、幂等重放、事务回滚及小迁移兼容。前端验证两入口的目标确认、成功信息、未知结果恢复及跨项目／会话隔离，再做最终构建。

在独立 QA 副本中，通过普通作者接口将改名 Markdown 稿对应到旧文稿，核对新版本、旧报告和原文保存及复检准备。需要写入的操作只发生在副本；本轮不提交新的模型审查。实现稳定后做一次集中审查与必要浏览器体验，合修后仅复查受影响部分，最后运行必要 CI 并更新本机。
