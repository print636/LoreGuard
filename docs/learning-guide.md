# LoreGuard 学习路线

## 第一次体验（15 分钟）

1. 双击项目根目录的 `启动LoreGuard.cmd`，浏览器会打开 `http://127.0.0.1:8000`。
2. 点击“一键运行原创样例”，观察抽取、状态索引、规则检查、报告四个进度阶段。
3. 展开“系统实际抽取了什么”，逐条对应原文。
4. 在“自然文本实验台”把“林澈的发色是黑色”改成“银色”，点击“运行当前文本”，确认事实冲突消失。
5. 对一个问题分别尝试“接受问题”“标记误报”“已解决”。

## 阅读代码的推荐顺序

1. `app/domain.py`：先理解核心数据类型和证据跨度。
2. `app/natural.py`、`app/parser.py`：理解无 Key 的保守抽取为何宁可漏报也不乱猜。
3. `app/pipeline.py`：理解抽取器和检查器的可替换边界。
4. `app/rules.py`：逐类跟踪状态索引和问题生成。
5. `app/service.py`：理解后台任务、阶段事件、失败状态和问题持久化。
6. `app/main.py`：理解 REST、SSE、反馈和一键演示接口。
7. `frontend/src/App.tsx`：理解页面如何创建项目、监听 SSE 并展示证据。

## 无模型与模型增强到底怎样分工

无模型模式不是“让另一个小模型猜”，而是一条完全本地、可重复的确定性流水线：先解析 Markdown/TXT/JSON 和明确中文句式，再做实体别名、时间、地点、物品与状态归一化，随后用关键词、稳定字符 n-gram 和实体关系建立候选证据，最后由五类规则比较结构化状态。同一输入会得到稳定结果，优势是可解释、低成本、离线可用；代价是只覆盖系统明确认识的表达，隐含指代、长距离因果和复杂转述容易漏掉。

模型增强模式只扩大“从普通叙事文本中抽出候选状态”的覆盖面，不让模型直接判定最终问题。每个分块连同原文全局行号交给 OpenAI-compatible Provider；返回记录必须经过 Pydantic 类型校验、证据范围校验和词面支持校验，然后与本地基线去重合并。最终冲突仍由同一套确定性规则产生，所以模型不能在没有两侧原文证据时凭空报错。超时、限流、非法 JSON、字段错误或局部分块失败时，系统保留已经验证的模型记录，并用全文基线兜底；终态失败会短路当前文档并打开运行级熔断，避免后续文档重复等待同一故障。

查看运行结果时不要只看“是否检出问题”：运行事件和诊断中的模式会说明这是完整模型增强、部分分块降级、模型完全降级后的基线兜底，还是主动关闭模型的纯基线。这样即使兜底结果恰好正确，也不能把它当成一次完整模型成功。

可以把两者记成一句话：模型负责“读懂更多写法并提出可验证的状态候选”，规则负责“基于可追溯状态作一致性裁决”。

## 需要你能亲口回答的问题

- 为什么当前基线不需要向量数据库？因为明确状态记录可直接精确比较；向量召回应服务于开放文本候选发现，而非装饰架构。
- 为什么无 Key 抽取器会漏句子？它只接受可解释模板，避免把不确定推断写成“事实”。开放文本覆盖率由后续模型抽取器补足。
- 为什么每个问题必须有证据？编剧工具的价值在可核对和可修订，而不是输出一个无法追溯的模型分数。
- 如何扩展新规则？实现 `ConsistencyChecker` 或在规则检查器中增加独立规则，并为正例、负例、时间边界和证据范围写测试。
- 如何接模型？实现 `NarrativeExtractor` 接口，通过 OpenAI-compatible Provider 返回 Pydantic 校验后的记录；失败时降级到基线抽取器。
