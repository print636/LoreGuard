# 批量导入恢复与项目基本信息 V2

## 项目基本信息

`GET /api/v1/projects/{project_id}/metadata` 返回小型元数据，不加载文稿正文：
`{id,name,description,created_at,metadata_revision}`。

`PATCH` 同一地址，提交 `{name,description,expected_revision}`。名称沿用创建入口的
1–200 字符边界，先去首尾空白，不增加字符黑白名单；简介沿用现有字符串约束。
额外字段、非正整数 revision 或空白名称返回 422。写入通过现有 CSRF／Origin 防护。
服务端只更新当前工作区、指定项目和匹配 revision，原子重算名称拼音排序键；有变化时
revision 加一，无实质变化不加一，但仍验证 revision。它不更改项目 ID、创建时间、
文稿、运行输入、角色档案或发布身份。

不存在和越权统一 404；并发冲突返回 409，`detail.reason_code` 为
`project_metadata_revision_conflict`，不在错误里返回服务器新值。用户可以另行读取最新
信息并核对；前端不能自动采用新 revision 后覆盖服务器。成功及错误响应均 `no-store`。
旧创建、目录及项目详情的响应保持原契约；编辑器打开时才读取这个新接口。

## 文件上传幂等收据

原 multipart `POST /api/v1/projects/{project_id}/documents` 兼容不发送操作标识的客户端。
新客户端可发送 `Idempotency-Key`：1–128 位 ASCII 字母、数字或 `._:-`，首尾空白会
去除，建议使用 UUID。非法字符／空键返回 400，HTTP header 超长校验返回 422。
它是一次文件导入操作标识，不是 API Key，不出现在响应、公开诊断或 URL。

标识只在本项目生效，与原始文件 bytes 的 SHA-256、精确文件名、替换目标、显式资料类型、
作用域、叙事上下文及 `multipart_document_parser_v1` 解析版本绑定。省略字段与显式选择
分开记录；不以同名或相同正文自动去重，不存原始 multipart body 或 Key 到日志。

收据与新文稿版本及上下文在同一事务提交，唯一约束 `(project_id,idempotency_key)`
是并发最终边界。相同标识／请求的重放返回原文稿 ID、版本和当时被替代的 ID 清单，
`deduplicated=true`；首次成功为 `false`，均保持 HTTP 201。若原稿后来被新稿替代，
重放不激活旧稿、不重新继承新上下文、不创建任何版本；响应中的 `active` 和当前
文稿上下文仍反映服务器当前状态，不能把重放当作又一次资料确认。

同标识用于不同文件或选项，返回 409
`detail.reason_code=document_upload_idempotency_conflict`。缺损收据不能安全核对时，
返回 `document_upload_receipt_unavailable`，不会猜测一个新版本。所有查询先验证项目
工作区；收据的项目与文稿有组合外键，不能指向其他项目的文稿。

## 网页恢复边界

- 成功行须核对 `id/project_id/name/version`，不能只凭 HTTP 2xx 判定；资料刷新失败不改成上传失败。
- 明确文件校验失败可保留待修正；网络、5xx 或无法核对成功响应应保留“结果待核对”。
- 只有用户手动重试同一未成功操作才复用标识和原 payload；成功文件不重传。更换文件、
  资料类型、作用域或替换目标属于新操作，须换标识。
- 本轮不缓存文件 bytes 到浏览器持久存储，不保证刷新或关闭标签后恢复 File 对象。
- 未指定类型／作用域时，同名文稿继承旧设置；新文稿按现有正文 `chapter`／`global` 导入。
  JSON 内容原样保留，但不会因此自动提升其文档身份、设定权威或发布状态。
- 项目创建尚无幂等收据。创建响应丢失时，先核对项目列表，不自动重建；文件失败后复用
  已确证创建的项目，不能再次创建同名空壳项目。

## 数据迁移及回退

`0024_project_import_foundation` 只在项目表原位增加带默认 1 的正整数
`metadata_revision`，另建成功上传收据表；不复制／重建项目表，不改已有故事及历史关系。
本地 SQLite 更新前应先停止自己的写入进程，在忽略目录保留文件级备份，再正常启动
Alembic 升级。升级验证只针对隔离合成旧库；它不是替真实库读取正文或执行评测。

若已有成功上传收据或修改过项目元数据，降级在任何 DDL 前拒绝执行，防止丢掉操作身份
和并发版本。尚未使用本阶段的空状态可回退：SQLite 3.35+ 对本迁移增加的 column-level
CHECK 使用原位 `DROP COLUMN`，不复制父表；对 `create_all`／采纳模式的 table-level CHECK
或旧 SQLite，保守保留默认 1 的兼容附加列，旧代码忽略它、重新升级会采纳它。空收据表
可以删除。PostgreSQL 同样先验证没有本阶段新状态，再移除附加结构。
这些是隔离测试可重复的迁移兼容合同，不是自动生产回滚。已有新状态时如需回退，须由
操作者停写、备份并选择受控方案；恢复旧备份不能无损保留升级后新增稿件或反馈。

本阶段不调用模型、不改变审查规则或宣称人工评测准确率，不新增自动发布、背景身份确认、
项目删除、团队共享、计费或生产备份服务。
