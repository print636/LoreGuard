# 角色一致性闭环 V1

## 目标与非目标

本阶段把 LoreGuard 从“同一字段的硬冲突检查”扩展为一个可审计的角色连续性工作流：正式设定和已发布历史剧情可以产生角色档案候选；候选只有经过用户确认，才会参与后续新稿审查；所有结论都必须回到冻结原文证据。

V1 只承诺两类能力：

- 识别有明确双侧证据的稳定偏好冲突，例如已确认的“喜欢蜜瓜”与新稿中明确、稳定的“厌恶蜜瓜”。
- 将证据充分的核心人格偏移列为高风险审查项，并区分成长事件、情境差异、伪装/撒谎、材料不足和分支互斥。

V1 不评价文笔、节奏、趣味性或角色魅力，不生成替换剧情，也不宣称理解完整人物弧线。单次反常行为不会自动升级为人格冲突；“在已导入材料中未找到原因”也不能表述成“角色没有原因”。

## 不可跨越的信任边界

权威、发布状态、版本顺序、分支关系、人工确认状态和证据原文均由服务端控制。模型只能：

1. 从服务端提供的冻结文档中归纳候选角色信号。
2. 在服务端给定的候选证据与引用白名单内判断是否存在矛盾、解释或材料缺口。
3. 输出简短的错误解释。

模型不能自行提升资料权威、确认角色档案、创造分支关系、引用快照之外的文本、绕过确定性晋升规则或生成修改稿。模型失败、非法 JSON、越界引用、上下文未解析和角色消歧不唯一都必须 fail closed。

抽取结果还必须通过服务端语义锚点校验：角色与对象必须出现在证据中，陈述的正负方向不得与原文相反，无关概括不能仅凭角色名或对象名的字符重合进入档案。即使是“喜欢/讨厌”这类直接偏好冲突，也必须经过一次独立的证据复核，不能只比较模型给出的极性字段。

## 文档权威

服务端根据文档角色、上下文确认状态和发布状态计算权威，不接受模型或客户端直接填写权威数值：

1. 已确认的世界/故事设定：`core_canon`。
2. 已确认的角色设定、已发布历史剧情：`formal_record`。
3. 当前未发布稿：`draft`。
4. 参考资料：`reference`，不能单独成为正式裁决依据。

同等级正式资料相互冲突时，应报告“正式资料自身冲突”，不能静默选择较新的记录。

角色档案快照保留 `authority_tier`。同一角色、同一特征、作用域与版本区间重叠时，`core_canon` 会遮蔽低一级的 `formal_record`；模型无权改变该顺序。候选的 `valid_from_release_ordinal` / `valid_until_release_ordinal` 必须覆盖待审新稿版本，目标版本不明时只能标记为材料不足。

## 结构化叙事作用域

旧 `document_role + story_scope` 保留为兼容层。V1 另存不可变的结构化上下文修订，并在分析创建时冻结：

```json
{
  "schema_version": 1,
  "timeline_key": "main",
  "release": {"key": "v1.2", "ordinal": 12},
  "branch": {"path": ["main", "route_a"], "exclusive_group": "ending_route"},
  "activity_key": "summer_event_2027"
}
```

作用域比较只有三种结果：`compatible`、`incompatible`、`unknown`。同一时间线且分支相同或为祖先关系时可比较；同一互斥组的兄弟分支、明确不同时间线不可比较；任一侧未解析或结构不完整时为 `unknown`。`unknown` 绝不等同于全局作用域，也不能产生确定冲突。

## 角色档案状态机

AI 归纳结果首先是 `pending` 候选。正式角色设定中的明确陈述可由一条证据产生候选；从历史剧情归纳人格模式至少需要两条独立证据。用户确认后才成为后续运行可用的档案项：

只有 `core` 或 `stable` 信号能进入这一稳定档案状态机。`temporary`、`situational` 和 `unknown` 信号可以作为当次观察或解释证据，但不会被晋升为稳定人物基线。

```text
pending -> confirmed
pending -> rejected
confirmed -> superseded（仅在替代候选确认的同一事务内）
```

审核为追加式记录，使用乐观锁和幂等键。旧决定不被覆盖。来源文档后来更新或停用时，历史候选仍保留冻结证据，但过期候选不能继续确认。

## 冻结与复现

一次分析必须在同一事务内冻结：

- 活动文档正文及内容哈希。
- 旧版文档角色/作用域。
- 最新结构化叙事上下文修订。
- 当时已经确认且适用的角色档案项。

`retry` 精确复制原运行的所有快照；`recheck` 读取当前活动文档、当前上下文和当前已确认档案。工作进程不能从 live 表重建角色档案。正文、上下文或角色档案任一发生变化时，复检不能错误宣称“输入没有变化”。

## 角色漂移判定

一级问题类别统一为 `character_drift`，细分为：

- `stable_preference_conflict`
- `core_trait_drift`
- `active_state_mismatch`
- `situational_pattern_deviation`

每个候选最终只能进入：

- `conflict`：证据充分的一致性问题。
- `needs_confirmation`：可能是伏笔、伪装、临时状态或缺少材料。
- `no_issue`：有充分成长/例外证据或作用域不相交。
- `unverifiable`：模型、检索、上下文、引用或材料覆盖不足。

只有 `confirmed` 档案项、兼容作用域、有效版本区间、低权威新稿和完整的基线/当前证据才可能产生 `conflict`。人格偏移在平衡模式下至少需要明确的反向旁白陈述，或两条相互独立的反向行为证据；单次行为最多进入待确认。抽取为空、角色无法唯一对齐、版本未知或任一模型步骤降级时，本次覆盖状态必须显示为 `partial` 或 `unknown`，不能用“0 个问题”暗示审查通过。

敏感度只控制确定性展示与晋升，不重新调用模型：

```text
保守展示集合 ⊆ 平衡展示集合 ⊆ 探索展示集合
```

提高冒险度不能改变原始证据等级，也不能把低置信候选包装成确定错误。

## 模型复核合同

角色一致性复核每次只处理一个已授权候选，返回严格结构：

- `verdict`: `contradicts | explained | needs_confirmation | insufficient_evidence`
- `explanation`
- `citations[]`

`contradicts` 至少引用一条已确认基线证据和一条当前新稿证据；`explained` 必须同时引用基线、当前新稿以及成长事件或例外证据。引用必须属于当前运行快照及服务端签发的白名单。漂移细分、权威、作用域、版本和材料覆盖均由服务端已有字段决定，不接受模型返回。原始模型响应、Prompt、API Key 和思维链不持久化。

## 运行边界

默认角色阶段共享 60000 Token 的内部准入预算。一次信号抽取逻辑周期独立准入最多 22000 Token（约 2.2 万），该额度由首次完整包和至多一次校验驱动的完整包重生成共同使用；它不是“每包各 22000”的额度。22000 为按最大分块、最大安全上下文和两次默认 completion reserve 验证后的有界默认值。每个 Provider 响应仍受默认 4096 Token 的 completion cap 约束；targeted 补抽按单个目标分别执行，但每次都从同一阶段剩余额度重新门控并记账，且须保留一次漂移 reviewer 的预算。阶段预算是调用前的共享准入上限；若上游违反输出上限或回报更高实际用量，诊断仍按较高值记账，因此它不承诺等同于 Provider 账单或绝对账单上限。信号抽取与漂移复核的单次逻辑调用，各自默认最多包含 2 次 Provider 传输尝试，且最多只能配置为 4 次；只有 Provider 判定为可重试的 429、5xx、连接超时、读取超时或传输错误才会进入下一次传输尝试。

信号抽取另有独立的“完整包生成”上限，默认和最大都是 2。首次响应在 JSON 结构、服务端字段、证据区间、对象、statement 或 targeted 绑定上有任何拒绝时，只有在剩余 Token 预算和总 deadline 均可容纳时，才会再发起一次“重新生成整包”的逻辑调用。第二次提示只携带服务端枚举的失败类别与内容无关的安全锚点，不携带上次原始响应或异常。空 `records` 是合法完整响应，不因包内校验失败而重生成。只有零拒绝且独立复现首轮全部严格绑定安全锚点的重生成包才能报告 `completed`，成功时只采用该干净包；两次均失败时不采用任何部分包。这里的总 deadline 覆盖一次信号抽取逻辑周期内的首次包与重生成包；focused targeted 的每个目标各自构成一个独立逻辑周期，不宣称存在跨整个角色阶段的共享墙钟 deadline。

focused targeted 首轮对某个目标返回干净空包后，如果该目标仍未达到下游判定所需的证据门槛，阶段最多进行一次空结果核验。核验视图只列出未排除且完整点名目标角色的原文行，保留原始全局行号；服务端仍在完整原文块上逐字绑定证据，并使用候选行号白名单拒绝局部序号、被省略行、跨行和已排除范围。所有目标都先完成首轮才进入核验，防止先遇到的空结果抢占后续目标的首轮预算。核验仍为空时保持空结果，不由规则生成角色信号；预算不足、取消或 Provider 失败均 fail closed 并明确标记覆盖不完整。

诊断中的 `attempted_calls` 表示逻辑模型调用数，因此一次验证驱动的整包重生成会使其从 1 增加到 2；单次逻辑调用内的底层传输尝试次数保留在 Provider 的无正文 telemetry 中。诊断只记录受控失败类别和计数，不记录原始模型响应。任一调用最终耗尽重试时，阶段仍按 `degraded` / `partial` 向上汇报，不会把缺失结果解释为“没有问题”。

## 用户界面

角色档案工作区位于 `/app/projects/{project_id}/characters`，包含：

- 角色列表与作用域/覆盖状态。
- 已确认档案及原文证据。
- 待确认归纳及确认/驳回操作。
- 最近角色漂移摘要。

完整漂移证据、反馈和修订复检继续复用现有问题报告，不复制第二套审查流程。界面必须区分没有文档、没有完成运行、没有识别到角色、没有候选、没有漂移、模型部分降级和候选过期，不能把任何降级状态显示成“没有问题”。

## 评测边界

V1 使用原创合成叙事集验证偏好正反、渐进成长、单次反常、伪装/撒谎、分支隔离、版本生效、临时状态和材料不完整。数据必须明确标注为开发者/AI 编写的原创合成集，而非真实策划语料或人工盲测。

计划门槛只有在冻结 holdout 上实际测量后才可写入结果：确定冲突 precision、recall、hard-negative specificity、双侧证据完整率、三次真实模型稳定率，以及跨项目/分支/快照泄漏为零。未运行或未达标的指标只能作为计划，不能写入 README 或简历成果。
