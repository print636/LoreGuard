# 第一阶段验收：AI-first 语义可信度与运行快照

更新时间：2026-09-06

## 目的与边界

第一阶段先解决“用户能否相信系统读懂了什么”和“运行结果是否对应确定输入”两个问题。验收集位于 `data/user-acceptance-v1/`，全部为原创虚构文本，不包含商业作品内容。

本验收集对开发者可见并用于开发，因此只能证明固定回归，不能称为盲测，也不能外推为网络小说、商业游戏或开放文本准确率。`manifest.json` 的文件引用、冻结数量、语义类别资格、状态机场景映射与非确定记录隔离已接入自动测试；真实模型的语义理解、完整问题命中和三轮稳定性仍必须另行运行，不能由 Mock 测试替代。

本阶段坚持 AI-first：疑问、假设、台词、谎言、转述、条件规则、分支作用域和跨章语义由模型理解；正则与确定性代码只负责文档边界、证据定位、状态约束、输出校验和安全兜底。不能为了少用 Token 把模型职责退化成本地句式匹配。Token 预算保留为异常循环和费用失控的安全上限，准确性优先。

同时，模型不得凭常识或猜测补造世界事实、规则例外、角色知识来源和未写出的因果关系。没有证据时必须输出“待澄清”，不能强行判定冲突或自行为故事补洞。

## 当前真实验收状态（2026-09-06）

新切换的中转/模型在 `thinking=disabled` 下通过生产路径 preflight，说明凭据、传输和最小 JSON 契约可用。随后运行冻结 `full × 1`：3 个 persona 的正式 Provider 调用均一次成功、HTTP 200、无空响应，但严格 gate 为 **0/3**，因此没有继续三轮稳定性验收。二游策划、小说作者、编辑案例的语义命中分别为 4/16、6/12、3/12；确认冲突完整证据命中为 0/2、0/0、0/3；待澄清命中均为 0/1；forbidden 命中为 0/4、1/5、1/3。三个案例均有未解决无效记录，第三案另有 batch 协议失败和后续分块熔断。

HTTP 成功不等于内容可用，也不等于完整模型覆盖。逐案耗时、Token、无效记录处置、AI 参与/覆盖及报告安全检查见 [2026-09-06 脱敏 checkpoint](provider-phase1-checkpoint-20260906.md)。默认 JSON 报告写在 Git 忽略的 `artifacts/`；本轮不公开中转 endpoint、key、Prompt 或原始响应。历史 complex-v3 与延迟成绩使用不同中转/模型或较早覆盖协议，不得沿用为本轮结果。

首次默认 runner 在首案主调用后进入 repair 路径时，因旧计数包装器缺少底层 Provider 属性转发而中断。该额外调用没有生成安全报告，其耗时和 Token 不可计量，未并入正式轮。随后代码已修复：Phase 1 与 complex runner 共用安全 `CountingProvider`，派生 repair 调用也会计入安全计数，相关 Mock 回归已通过。repair pass 是受限的语义标签补救调用，不是 Agent。

## 冻结数据规模

| 用户身份 | 文档 | 主要能力 |
|---|---:|---|
| 二游剧情策划 | 3 | 设定与正文、互斥分支、同分支地点冲突、规则例外、疑问、假设、已知谎言 |
| 网络小说作者 | 1 | 仅正文、正文内规则、否定、单向条件、开放问题、可能性和待澄清因果 |
| 长篇编辑/审稿人 | 2 | 仅正文多章节、跨章物品/知识/地点证据、匿名转述、条件规则和缺失状态转移 |

## 语义契约

系统必须把结果分成以下层级：

1. `confirmed_canonical`：设定档、明确规则、清单或正文反复确认的权威事实，可以参与确认冲突。
2. `confirmed_narrative`：旁白明确发生，并排除了回忆、幻象、猜测等歧义的事件或状态，可以参与确认冲突。
3. `quoted_claim`：角色台词、匿名信、转述或明确谎言，只能表示“某人声称了什么”，不得冒充旁白事实。
4. `tentative`：如果、也许、可能、尚未验证等假设，不进入确认冲突。
5. `open_question`：没有得到回答的问题，不得把“是否”里的“是”拆成肯定事实。
6. `clarification`：现有证据不足而需要作者或策划补充的缺口，必须与确认冲突分开展示和计数。

`quoted_claim` 并非永远无价值：未来可以用于检查角色陈述和已知事实的差异，但必须明确标为“声称/可能撒谎”，不能直接污染世界事实。第一阶段不要求把谎言本身报成错误。

## 三组人工验收

### 1. 二游剧情策划

输入 `game-planner/world.md`、`route-a.md`、`route-b.md`，并让系统知道 A、B 路线互斥。

必须确认：

- 弥音无书面授权却使用赤钥进入封锁区，属于世界规则冲突。
- A 路线同一时刻弥音出现在观星厅和下层货舱，且无传送、回忆或投影，属于地点冲突。
- 推车食物是否安全属于未回答问题；世界设定只说明它不自动属于餐车供应，不能猜测其真实效果。
- “恢复体力或昏睡”是两种假设结果，均未发生。
- 弥音关于未读日志的台词是明确谎言，不得与旁白记录合并为普通事实。
- A 路线观星厅和 B 路线货舱不能跨互斥分支产生地点冲突。

### 2. 网络小说作者

只输入 `novelist/chapter.md`，不提供世界观文档。

必须确认：

- 正文内反复确认的古井规律和“从未失效的旧律”可成为本故事的权威事实，证据来源仍标记为正文。
- “没有银铃”“没有豁免”“门没有打开”保持否定语义，不能抽成对应正面事件。
- “若下雨则熄灯”是单向条件，不能由无雨反推出灯不可能熄灭。
- 正文只确认陆遥出现在石门另一侧，没有确认他穿过石门；暗渠也只是猜测。因此当前只能提示“抵达路径待澄清”，不能确认违反银铃规则。
- 明确标注为谎言的台词只作为角色声称保存。

这个案例故意不提供确认冲突，用于防止系统为了展示“有用”而强行制造问题。

### 3. 长篇编辑/审稿人

只输入 `editor/chapter-01.md` 和 `editor/chapter-02.md`，不提供单独世界观。

必须确认：

- 唯一星钥已经转交并持续由林岑保管，乔予随后使用真实星钥，形成物品状态冲突。
- 乔予在坐标首次拆封前准确使用它，且文本排除猜中与未来读取，形成知识越权。
- 同一主线同一时刻林岑在西塔和东港，且交通时间不足，形成地点冲突。
- “是否有另一把星钥”是编辑提出的问题，不能自动生成第二把钥匙，也不能用未回答问题消除既有冲突；它应成为缺失状态转移的待澄清项。
- 匿名信只是一项未验证声称，不能证明蓝色账册已销毁。
- 红灯导致关门是单向条件；蓝灯时开门不构成冲突。

## 运行状态机验收

### 文档快照

- 创建 R1 时冻结当前文档 ID、版本、内容哈希和作用域。
- R1 排队后上传 v2，R1 仍只分析 v1；全新 R3 才分析 v2。
- 失败或取消后的“重试同一次输入”必须继承原快照，不能静默读取当前活动版本。

### 幂等执行

- 两个 worker 收到相同 `run_id` 时只能有一个获得执行权。
- 完成的 `run_id` 再次投递时直接幂等返回，不再调用模型、不重复计费，也不重复写问题、记录和事件。

### 取消

- `queued/running` 可请求取消，重复取消保持幂等。
- 系统在下一个安全检查点停止，并且取消后不再发起新的模型调用。
- 已经产生的审计事件可以保留，但半成品不得作为完整报告发布。

### 旧运行

- 没有快照元数据的旧结果仍允许只读查看，但必须显示“输入版本未知”。
- 系统不得把当前活动文档伪装成旧运行原输入。
- 无法证明原输入时，不允许承诺“按原输入重试”；应引导用户基于当前版本创建新分析。

## 执行方式

### Runner 参数语义

`--suite pilot` 仅运行冻结清单中的首个案例，用于尽早发现配置、传输或兼容性问题；它不是“三个案例各运行一次”的严格 pilot。三个案例各运行一次必须明确使用：

```powershell
python scripts/run_phase1_model_acceptance.py --suite full --repeats 1
```

正式稳定性验收仍使用 `--suite full` 的默认 3 次重复。`--case-id` 会显式选择单一案例，不改变该案例的完整模型参与判定。

Runner 支持 `--timeout-seconds`、`--max-attempts` 和 `--circuit-failure-threshold` 临时覆盖 Provider 请求超时、重试次数和熔断失败文档阈值；这些覆盖只在当前 Python 进程的单次案例调用中生效，调用结束后恢复内存中的原值，不写入 `.env`。`--per-case-token-budget` 是每次案例运行的 Token 安全上限，实际值还会受 `--max-total-tokens` 剩余额度约束。

JSON 报告按案例记录实际生效的脱敏模型标识 SHA-256、上述运行参数、thinking 是否显式配置及其 `disabled`/`enabled` 模式、每案例总耗时及可获得的 Provider 逻辑调用聚合。未显式配置 thinking 时模式为 `null`，与 Provider 默认行为一致。报告不记录 endpoint、API key、Prompt 或原始响应正文。

Phase 1 与 complex runner 使用同一个安全计数包装器；模型主调用和抽取器派生的 repair 调用都计入逻辑调用统计。Compose 将 thinking 配置同时传给 API 和 worker，空字符串先归一为 `None`，不会把空白误当成显式模式。

### 无效记录最终处置

`invalid_records` 是兼容既有报告的原始/observed 计数，包含随后可能被语义标签 repair pass 恢复的记录，不能单独代表最终覆盖缺口。新版诊断同时提供 `recovered_invalid_records` 与 `unresolved_invalid_records`，三者必须满足 `invalid_records = recovered_invalid_records + unresolved_invalid_records`。repair 失败后保留的安全非确定 trace 仍属于 unresolved，不能冒充已确认恢复。

新版运行只有在 `unresolved_invalid_records=0`、`repair_failed=false`、`repair_post_invalid=0`、计数守恒且没有空响应或分块失败/跳过时，才可判定模型覆盖完整。成功 repair 会披露原始无效与恢复数量，但不会仅因 `invalid_records>0` 被误判为部分覆盖。缺少新版字段的历史报告继续按 `invalid_records` fail-closed。

### AI-first provenance 前置条件

模型调用成功、所有分块成功以及 `model_used=true` 都只能证明模型参与过本次运行，不能证明最终保留下来的每条语义、冲突和待澄清项来自模型。特别是 baseline 与模型结果去重、语义质量转换、排序和 issue 去重之后，运行级布尔值无法归因到单条最终记录。

Runner 因此对单条 provenance 采用 fail-closed：缺失、旧版、重复 fingerprint、未知来源或不支持的 schema 都不得计入 AI-first 指标。当前后端已经返回 schema v1 的最终 directive provenance；2026-09-06 真实轮中三案仍未达到完整覆盖，确认冲突也没有形成可验证的 issue provenance，因此三个案例的完整 provenance gate 均未通过。自动测试里的合成 provenance 只验证评分契约，不能冒充真实后端能力。

`diagnostics.provenance` 的持续验收契约如下；即使字段存在，只要内容缺失或无法覆盖最终结果，仍必须失败：

- `schema_version: 1`。
- 每条最终 directive 的稳定 fingerprint 与 `sources`；允许 `baseline`、`model` 并存，去重时必须取来源并集，不能让 baseline 覆盖模型贡献。
- 每条 clarification 除自身证据外，列出该 finding 所依赖的全部 `contributing_evidence`（相对路径、行号）；manifest 要求的多条证据必须全部命中。
- 每条最终 issue 的稳定 fingerprint、`derivation` 和 `evidence_sources`。第一阶段冲突允许、也要求 `derivation` 包含 `deterministic`，但其 `evidence_sources` 必须包含 `model`；纯 baseline 证据不能获得 AI-first 通过。

fingerprint 使用 UTF-8、键排序、非 ASCII 不转义的规范 JSON 后取 SHA-256。directive 载荷为最终记录的 `kind`、评分语义类、确定性规则资格、相对路径、证据起止行和排序后的 attrs；issue 载荷为类别与排序去重后的 `[相对路径, 起始行]` 证据。后端若改写最终记录，必须对改写后的记录计算；同一 fingerprint 出现多条 sidecar 记录会被视为归因歧义。

Runner 不从文本、文件名、模型执行计数或最终输出形态反猜来源。

1. 每个案例创建独立项目，按 manifest 声明的文档角色与作用域导入。
2. 使用当前目标模型完整分析；预期 manifest 不得进入模型 Prompt。
3. 确认诊断为完整模型参与，无降级、无分块跳过、无因预算而截断。
4. 对照 manifest 人工核验语义类别、证据、确认冲突、待澄清和禁止转换。
5. 每个案例独立执行 3 次，记录脱敏模型标识、thinking 安全模式、运行参数、Token、延迟、失败与结果差异；不记录 key 或 endpoint。
6. 另行用 Mock/故障注入验证 7 个状态机场景；状态机验收不需要消耗真实模型 Token。

## 通过门槛

- 5 个确认冲突全部命中正确类别，并引用 manifest 要求的完整证据。
- 3 个待澄清项全部单独展示，不能计入确认冲突。
- 11 条 `quoted_claim/tentative/open_question/clarification` 语义全部不进入确认冲突引擎。
- 所有 `forbidden_findings` 为 0。
- manifest 中 12 条 `forbidden_findings` 必须逐条运行对应的显式断言并写入报告；任何命中都会失败。新增或改写的禁止项若尚无执行规则，状态为 `unevaluated` 并同样失败，不能靠模糊文本相似度自动判为通过。
- 每条必需语义与待澄清项的最终 directive provenance 都必须包含 `model`；待澄清项必须覆盖 manifest 列出的全部证据。
- 每个确认冲突必须证明由确定性检查器推导，同时其证据 provenance 包含 `model`；纯 baseline 或无法归因的 legacy 结果只能用于降级安全验证。
- 必需语义证据定位命中率至少 95%。
- 每个案例 3 次运行的语义类别、确认冲突和待澄清项完全一致。
- 7 个状态机场景全部通过。
- 任何一次模型降级、拒绝记录、跳过分块或输入截断，都不能计为本套 AI-first 验收通过；结果可以留作故障证据。

## 仍存在的产品决策歧义

以下问题不能由模型暗自决定，进入实现前需要明确产品契约：

1. `confirmed_canonical` 在“只有正文”模式下的权威强度：本验收暂定“反复确认”“从未失效的旧律”“清单确认”等强措辞可成为故事内权威事实，普通旁白只算叙事事实。
2. 确认冲突与待澄清是否可以同时指向同一证据：本验收允许。例如唯一钥匙冲突已成立，同时缺少转移路径仍值得作者补充；待澄清不能自动降低已确认冲突。
3. 分支作用域如何输入：文本 JSON 与 multipart API 已提供显式 `document_role`/`story_scope` 字段，并冻结进运行快照；同名版本省略字段时继承上版，全新文档安全默认 `chapter/global`，始终不能用文件名猜分支。当前网页尚未提供这两个字段的编辑控件。
4. 角色说谎是否单独提示：本阶段只要求正确区分声称与事实，不要求把说谎判成剧情错误。
5. 后端已通过独立只读接口返回 `clarification/open_question`，并与 confirmed issues 分开计数；网页整合、模型设置、 `.docx` 传输、关系图/时间线按需生成属于后续输入与界面验收，不在本语义/状态冻结集里冒充已完成。

通过本阶段只能宣称“固定原创案例的复杂语气分类、证据化冲突和运行快照达标”，仍不能宣称开放文本生产准确率、真实长篇能力、RAG、Agent 或多人生产部署已经完成。
