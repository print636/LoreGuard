# 分析运行创建可靠性

## 客户端契约

`POST /api/v1/projects/{project_id}/analysis-runs` 和
`POST /api/v1/analysis-runs/{run_id}/retry` 接受可选的 `Idempotency-Key` 请求头。
不发送该请求头的旧客户端保持原有行为：每次请求都会创建一个新运行。

键只在当前项目内生效，必须由 1–128 位字母、数字或 `. _ : -` 组成。客户端应为一次
用户操作生成一个新键，并在网络超时后的同一次重试中复用；新的用户操作必须换键。
服务端不在响应、公开诊断或 URL 中回显该键。
同一项目内的键还绑定本次操作语义：普通启动与重试不可共用键，两次来自不同旧运行的重试
也不可共用键；这种误用返回固定的 `409 idempotency_key_conflict`，不会回显键值。

响应包含：

- `id`、`project_id` 和当前 `status`；
- `retried_from`，用于识别使用旧运行冻结输入创建的重试；
- `deduplicated`，表示本次请求是否命中了已经存在的运行。

`GET /api/v1/analysis-runs/{run_id}` 返回精确运行及其 `project_id`。调用方可据此校验页面
URL 中的项目与运行是否匹配；服务端仍会按工作区校验归属，未知或跨工作区运行统一返回
`404`，不暴露资源是否存在。

## 数据库与并发边界

`analysis_runs.idempotency_key` 可空，数据库以唯一索引约束
`(project_id, idempotency_key)`。请求路径的“先查询”只是常见重复请求的快速路径；两个并发
请求都未查询到记录时，唯一索引决定胜者，失败事务回滚后读取胜者。因此同项目同键只会
保留一个运行、一组冻结输入，且只有创建胜者的请求进入调度。

重试运行始终复制来源运行的不可变输入快照，不读取项目当前活动文档。同键命中已经失败的
运行时只返回该运行，不会重新投递；需要再次尝试时，客户端应调用重试接口并使用新键。

## 调度失败

运行和冻结输入在调度前提交。如果 Celery 投递或本地线程启动抛出异常，服务端会把仍为
`queued` 的运行原子更新为 `failed`，写入一条 `failed/100` 终态事件，并返回 `503`、
`Retry-After` 以及可恢复的 `run_id`。持久化错误和 HTTP 正文使用固定安全文案，不保存或
回显底层异常、Provider 地址、密钥等信息。

## 不承诺的能力

这一机制提供“运行创建幂等”和调度失败后的可见终态，但不宣称消息或模型调用
exactly-once。当前没有事务型 outbox；调度发生在数据库提交之后，极窄的传输不确定窗口
仍通过运行状态、终态事件和 worker 认领规则保守处理。每日 Token 配额也仍是单数据库的
非原子创建前检查。
