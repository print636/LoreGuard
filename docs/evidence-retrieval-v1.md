# Evidence Retrieval v1 冻结评测边界

## 用途

`data/evidence-retrieval-v1/` 是 LoreGuard Evidence RAG 的第一版开发者可见检索评测集。它只冻结“给定问题应召回哪些原文证据”及隔离负例，不实现或指定检索算法。建立本套件时没有查看检索实现，也没有调用模型。

它用于比较 keyword-only、dense-only 和后续混合检索配置，不能证明开放剧情、商业游戏文本或真实用户数据上的准确率。全部世界观、章节和问题均为本项目原创，不含商业游戏剧情。

## 构成

- 共 44 题：16 题 dev、28 题 holdout。
- dev 的目标问题只使用“雾港钟塔”，另有一个不含题目的“云剧院”错误项目夹具；holdout 的目标问题只使用“白烬档案馆”和“星茧列车”。同一世界不会跨 split，错误项目负例也不会跨 split 引入语料。
- 每题包含原创中文 query、难度、能力标签，以及一个或多个精确到文档版本和原文行区间的预期证据。
- 22 题标为低词面重叠。测试会独立复算中文字符 bigram 覆盖率，不能只信人工标签。
- 覆盖别名、例外规则、跨章因果、角色知识获得、时间和物品状态。
- 三道隔离题显式列出旧版本、错误 profile、同项目错误文档和错误项目候选。错误文档与错误项目语料包含相似表面词，避免用完全无关文本假装隔离测试。

## 冻结与泄漏规则

`freeze.json` 固定 manifest 和全部语料文件的 SHA-256、字节数与行数。修改任何冻结文件都必须创建新的数据集版本，不能覆盖 v1 哈希。

可以在 dev 上选择查询指令、权重、阈值、top-k 和融合方式。holdout 首次用于选择或修改实现后，就不再是未参与调优的 holdout；后续泛化声明必须另建冻结版本。评测报告必须同时保留数据集哈希、模型 revision、运行时镜像 digest、embedding profile、chunker version 和检索配置。

## 建议评分口径

每个返回候选必须先满足项目、当前文档版本、内容 snapshot、chunker version 和 embedding profile 的隔离约束。旧版本、错误项目或错误 profile 出现在允许结果中均视为隔离失败，不因语义相似而豁免。

建议至少报告：

- `Evidence Recall@k`：每个预期行区间是否被正确 snapshot 的返回 chunk 覆盖；多证据题分别计数。
- `All-evidence Success@k`：一道题的全部预期区间是否均被覆盖。
- `MRR` 或首个正确证据排名。
- 隔离失败数；安全门槛应为 0。
- P50/P95 延迟、失败率、索引构建时间与存储量。

若 chunk 只与目标行区间部分相交，报告必须明确采用“相交”还是“完整覆盖”口径，不能在看到结果后切换。推荐主指标使用完整覆盖，部分相交仅作诊断。

## 机器校验

`tests/test_evidence_retrieval_v1_manifest.py` 检查：

- manifest/freeze schema 和所有文件哈希；
- 任务数量、split 与世界观隔离；
- 文档版本、证据行范围和当前版本约束；
- 必需能力标签与低词面重叠阈值；
- query 不机械复制长答案片段；
- 四类隔离负例真实存在且确实处于允许 snapshot/profile 之外。

该测试只验证数据合同，不运行检索，也不构成质量成绩。
