# 角色特征“作者批准稳定轴”设计 RFC

状态：提案，尚未实现。本文不改变当前角色抽取、候选确认、快照或评测结果。

## 背景与目标

模型从设定中抽取的 `trait_key` 是自由生成的标签。当前非对象类角色特征主要依靠该标签进行跨文档匹配；同一个行为语义轴可能因措辞不同而漏配。冻结的 `character-ooc-transfer-v1` 严格运行在正式候选选择处失败：霁青的来源锚点候选存在，但模型标签不在预注册的 `(trait_key, polarity)` 允许项中。来源锚点诊断不能代替严格验收，且另有基线不完整、已解释案例误报等独立问题。

目标是让**作者对语义轴的确认**成为稳定、可追溯的项目数据，使模型标签变化不自动改变比较身份；不要求作者批准模型对原文的每个概括，也不让标签相似度取代原文证据。

## 概念和比较边界

| 概念 | 含义 | 身份作用 |
| --- | --- | --- |
| 原文证据与 `value` | 设定/历史中的原句及其最小主张 | 证明候选内容；不可由批准轴反向生成或覆盖 |
| `model_trait_key` | 模型提出的中性语义轴名称，即现有 `trait_key` | 保留为来源和诊断信息；不是新的权威身份 |
| 作者批准轴 | 项目内的轴 ID、中文含义及版本，例如“涉及同伴安全的撤离路线决策是否征询当值伙伴” | 同轴匹配的稳定身份；方向不写入轴本身 |
| `polarity` | 对该轴的正/反方向 | 与轴分开保存；不能从字面褒贬自动推断 |
| `key_object` / `comparison_key` | 原文绑定的对象及现有冻结对象键 | 对象边界仍独立生效，不被批准轴吞并 |
| 权威、作用域、发布序号 | 正式设定/已发布历史、分支与生效期 | 继续决定哪条基线可用；批准轴不提升权威 |

推荐项目内使用不含自然语言含义的轴 ID，并为轴定义记录不可变版本；显示名称可改，但不能借改名把两个不同轴悄悄合并。`core_personality`、`speech_pattern` 等无必需对象维度以批准轴匹配；`value`、`behavior_boundary`、`current_state` 必须同时匹配批准轴和原有精确对象键；`preference` 继续以精确偏好对象为主，不能因“食物偏好”轴相同而把蜜瓜与葡萄合并。情境、叙事分支、角色归属和权威过滤仍是额外条件。语义相关不等于同轴：例如“征询同伴”与“等待上级命令”不能仅凭“路线决策”共享身份。

批准轴只表示“比较什么”，不预判新稿是否矛盾。草稿观察仍须原文证据、角色行为归属、方向和对象校验；证据不足时弃权或要求作者确认，不靠轴 ID 输出问题。

## 存储、审核与版本

建议增量增加项目级 `character_trait_axes`（轴 ID、维度、定义、显示名、版本、创建者、时间）和候选的批准轴绑定记录（候选 ID、轴 ID/版本、审核者、审核时间、预期候选修订）。模型原始标签、候选证据、`value`、`polarity`、`comparison_key` 和候选指纹保持原样。绑定由作者确认，不能由模型调用自动写入。确认候选与绑定轴应在同一事务中完成，并保留幂等键、并发修订、项目归属和 CSRF 校验；拒绝轴与候选维度不符、证据已过期或用户无权的请求。

每次分析继续冻结输入快照：同时记录原始标签、批准轴 ID/版本、定义摘要、对象键、方向及原有来源/权威/作用域字段，并纳入快照哈希。后续轴定义变更只产生新版本；既有运行和报告不回写。跨项目不共享轴 ID。已确认特征发生同轴冲突、替代或权威覆盖时，必须基于批准轴**加**对象、范围和权威规则重审现有校验；不能只改草稿匹配而漏改确认冲突检查。

## 旧数据兼容

旧候选和旧运行快照没有批准轴；迁移字段保持 `NULL`，不从 `value`、旧 `trait_key` 或证据中猜测回填。旧快照按既有逻辑读取并标明“未批准轴”，其历史结论不改写。已确认旧候选若要获得新轴，应由作者显式发起绑定审核事件，只影响**之后**创建的快照；首次版本可暂不提供旧候选升级入口，但不得把无入口描述为自动升级。新候选缺轴时也不能暗中与已批准轴候选合并或替代。

## 作者体验

候选卡同时展示：原句与行号、资料权威和版本、模型原始标签、轴的中文定义与方向、对象、适用范围，以及项目中可能相关的已有轴。作者可选择已有轴或创建新轴，再确认候选；相似候选仅作建议，不自动合并。若两个候选同轴但取值/方向冲突，或同名轴指向不同对象，界面显示冲突理由并要求明确处理。批量审阅可减少操作，但每项绑定仍须可追溯。尚未审核的轴不作为正式基线。

## 分步落地与测试

1. 先增加数据模型、迁移和只读展示；验证旧数据 `NULL`、旧快照哈希及现有分析结果不变。
2. 增加轴创建/选择和候选原子确认 API，再接 UI；测试权限、CSRF、幂等、并发修订、过期资料、错误维度，以及原始证据和标签不可改写。
3. 让新运行的正式快照冻结批准轴，草稿定向抽取复用该轴；同时改造候选确认冲突、替代、权威屏蔽和报告 trace。测试同轴不同方向、异轴相似词、同轴不同对象、分支/情境隔离、旧无轴回退与历史快照不变。
4. 做模型异常和质量回归：非法 JSON、超时、材料覆盖不完整时不能假装“无冲突”；角色错归属、单次例外、正式成长桥梁必须保留原证据门槛。

## 评测边界

`character-ooc-transfer-v1` 的 Oracle、正文和首次运行前冻结的哈希不修改；其严格选择器要求**模型原始 `trait_key` 精确命中预注册选项**。作者批准轴是不同的产品流程，不能把来源锚点确认或作者改轴冒充为该严格门槛通过。旧严格失败报告仍保留；旧材料可用于开发回归，但只能标为开发者可见诊断。

为衡量新流程，应在首次运行前另行冻结新材料、人工标注的角色—轴—对象—方向、作者审核协议、预期问题及证据、评分脚本和哈希。报告至少分别给出候选召回、轴绑定正确率/待确认率、草稿观察覆盖、问题误报/漏报、材料覆盖与成本，并执行多次独立全流程运行；部分运行或人工补救单列，不汇入自动通过率。若测试者已见材料，明确标注开发者可见，不能声称盲测或开放文本泛化。

## 风险与待定决策

- 人工审轴有成本；若默认替作者确认，原有自由标签漂移会换成错误合并。先测真实审核耗时，再决定是否加入带置信度的批量建议。
- 轴定义过宽会误报，过窄会漏报。建议用项目内轴 ID 和中文定义，而非仅存一个可变英文字符串；模型只提议，作者决定。
- 含糊设定可能没有可靠语义轴。允许“不确定/暂不建立基线”，不要为了提升覆盖率强制归类。
- 待定：既有已确认候选的显式升级入口是否纳入首版；轴版本变更是否必须二次确认所有关联候选；批量审核一次最多处理多少条。这些不影响先建立新候选的安全边界。
