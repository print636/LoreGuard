# OOC 网站判断策略对齐计划

日期：2026-11-03。状态：**只读审计后的待实施计划，不是已完成能力或质量结论**。

本文由用户已经确认的产品规则推导，制定者没有读取本轮真人答案、人工裁决、私有 gold 或模型预测。审计只查看公开源码与既有协议，没有修改网站、Prompt、运行配置、执行器或测试，没有调用模型。本文不依据本轮具体题目或标注分歧设计修复。

当前离线作答与裁决已采用[关系方向 V4](annotation-relations-v4.md)，网站实际判断仍保留多处双事件门槛。离线工具支持某项标注，不代表网站或模型已经支持该项判断。本文只计划对齐这个差距，不扩大到模型训练、跨模型比较、长篇增量处理、部署或新业务功能。

## 已确认的产品规则

1. 单次明确、证据完整的冲突可以成为正式问题；有歧义的反常表现保留为待复核线索。多次表现只增强证据，不再是固定次数门槛，更不映射为固定冲突概率。
2. 人物、行为归属、比较轴、对象、情境、时间与材料权威仍须核对。允许有原文依据的跨分句承接和有限推断，不以相同字样是否出现替代语义判断。
3. 成长材料与每条新稿表现分别建立关系：能解释、与表现相反、尚不能确定。同一成长可以解释表现 A，同时与表现 B 相反。
4. 正向解释不能被用于支持其已解释事件的正式冲突；明确反向材料不能被误当作开脱理由，也不会自动产生正式冲突。未决材料不能充当确定解释或确定反向依据。
5. 解释或未决关系作用于其所关联的整个事件，不能通过拆开同一事件的句子绕过。无关事件的不确定性不应机械否决另一条明确冲突。
6. 若整题判断依赖未决关系，保留疑点；若不靠该关系就已经与设定一致，仍可判断无问题。不新增“出现未决关系则整题不得无问题”的硬规则。
7. 正式问题与待复核线索继续分别展示、计数和处理；模型失败或覆盖不足不能冒充无问题。原文证据、冻结版本、作者确认和权限边界不放宽。

以上只调整一致性判断，不把“违背某条设定”直接解释为“人格已经永久改变”，也不增加自动改写或剧情质量评价。

仍需补齐的是**可靠的已审查事件来源**：目前普通 C 的已审查集合主要来自范围轴审查或 `event_independence=yes`，约 1233–1257 行。普通单行为没有相应记录时，不能仅因最终报告出现 C，就由 runner 替模型制造已审查事件。网站应先输出服务端校验过的事件与当前引用绑定，再由 runner 精确投影。

正式报告当前必要引用投影主要限于 B/C。成长反向可作为带方向的辅助上下文保留；不得将 G 伪装成 B/C，也不得把人工 gold 中的辅助关系当成模型已经给出的判断。若将来扩展正式报告的可展示角色，需要同步约束原生报告、trace 与评分投影，不能只改某个字段。

## 两步最小实施范围

### 第一步：单次明确冲突贯通

统一候选准入、主审查 Prompt／响应、最终晋升、引用绑定、单事件诊断和执行器投影。至少一个经过核验、语义明确且没有适用有效解释的事件可以支持正式问题，不再因为缺少第二次行为直接降级。

已有的跨句主体归属、目标绑定、设定权威、文档版本、材料覆盖和原文引证继续使用，不重写抽取系统。同一事件的多个片段仍不能被计算为多次；但不满足“两次独立事件”本身不再否决已经明确的一次冲突。歧义、假设、他人行为或无法归属的动作继续保留待复核／无法核实状态。

不能只删最终的 `two_independent_behaviors` 门闩，否则上游仍可能不调用模型、关系／动机提前降级，或报告无法被执行器正确识别。

### 第二步：逐表现成长方向贯通

先确定新版关系响应与 `SupportEvidence` 兼容合同，再实施关系复核、支持生成、事件适用、最终裁决和诊断投影。新记录须明确方向，不接受未知值回落为正向解释；同源材料针对不同目标的方向和强度分别保存。

旧 v2 支持记录保持原解释语义与旧运行可读性，不把旧记录自动改为反向证据。新版本中，正向解释才可计入已解释覆盖；反向关系保留为辅助证据；未决关系只影响其适用事件。既有来源权威、已发布成长、时间顺序和防止行为自我解释的约束不因新增方向而取消。

不在本步自动将成长提升为新的作者确认基线，不自动撤销或替换角色特征，也不新增作者操作流程。

### 实施组织与集中验证

可由一位开发者负责 `character_drift.py`，另一位在共享合同确定后负责 `character_explanation_review.py`；涉及 `SupportEvidence` 的改动先约定唯一写入者。stage、provenance 和 runner 由整合者统一处理，避免同时改同一大文件。

集中验证覆盖：单次明确冲突、有歧义反常、正向成长、反向成长、同源混合方向、未决关系局部影响、同事件多片段及原文引证绑定。使用另外虚构的开发材料；不让真人封闭题进入 Prompt 示例或针对性单元测试。先完成同批相关开发再集中检查，只对失败或实际受影响部分补跑，不为本计划重跑整站、Docker 或全量 CI。

## 运行前必须冻结的内容

1. 真人部分：两份原始独立提交及其摘要、真人裁决、最终手册／公开策略与私有 gold；不回改原提交，不由 AI 补裁决。
2. 产品部分：实际执行的是现状策略还是适配后的策略，候选、主审查、成长方向及晋升合同对应版本。
3. 软件部分：网站运行时来源、Prompt／schema、执行器与评分源码清单；不能运行中途修改后继续记为同一次冻结执行。
4. 运行部分：真实模型与 Provider、开关、预算、超时、敏感度、隔离实例、运行次数及固定 `run-config.json`。
5. 评分部分：公开包、作者配置、执行冻结、质量门槛及 commitment 的全部绑定。

现有工具要求运行配置在 `build-gold` 前选定。源码或运行策略发生变化后，应按原协议重新建立相应冻结与 commitment，保留旧产物；不能把旧 commitment、现状基线模型报告和修复后配置拼成正式评分输入。

## 收到真人裁决后的两种顺序

这两种方法都可明确记录，但回答的问题不同。审计者只列出含义；以下选择由主智能体作出。

**本阶段采用先冻结现状基线。** 这与当前“先完成真人封闭评测，再根据真实失败修复”的目标一致。网站已知的策略落差要在结果中单独归因，不能据此断言模型推理不足。真人复核完成前不运行该批次；首次结果原样保存，随后按需求和失败修复。用于修复的题只作为开发／回归验证，后续同题成绩不重新包装成独立封闭验收。

| 方法 | 执行顺序 | 可以说明什么 | 不能说明什么 |
| --- | --- | --- | --- |
| 先冻结现状基线 | 冻结当前尚有旧门槛的网站与配置 → 封存真人 gold → 一次真实运行与正式评分 → 揭盲分析 → 按需求／失败修复 | 真实记录当前版本在新人工标准下的表现，分清既知策略落差、覆盖缺失与语义误判 | 不能把旧双事件门槛导致的漏报直接归为模型推理不足；也不能把后续同题改进成绩称为新一轮未见答案的验收 |
| 先做纯需求适配 | 在不看真人答案及模型预测的条件下完成上述两步 → 用无关合成材料检查 → 冻结适配后源码与配置 → 封存真人 gold → 一次真实运行与正式评分 | 检验与已确认产品规则对齐后的首次冻结版本，减少已知策略不一致对评测的干扰 | 没有记录适配前真实模型基线，不能补造“修复前后提升”；也不能借纯需求之名按封闭题内容定制 |

若选择第二种，开发者应保持对真人具体答案与分歧内容不可见；材料处理者只提供完整性、冻结一致性及是否需要真人裁决等流程状态。若开发者已经据某个封闭 case 的标签或具体模型失败修改实现，该 case 不再满足未揭盲条件，不能通过重新命名批次恢复其封闭身份。

## 揭盲后的修复与报告边界

首次冻结评分与揭盲分析是两个阶段。先保存原始运行、评分和失败状态，再定位真实失败属于抽取、检索、主体归属、关系判断、晋升策略、引证或覆盖问题；不先挑最好结果，不把未核实、失败或部分覆盖计为正确无问题。

某个 case 一旦因其具体答案或模型错误被用于修改代码、规则或 Prompt，即转为 DEV／回归样本。修复后重跑它可以验证该问题是否改善，但必须标为修复验证，不能仍宣称是未见过答案的封闭测试。下一次独立封闭验收需要未揭盲的新样本；本阶段不主动扩充大量刁钻场景。

小样本结果只用于决定工程方向，不推断开放文本准确率、生产质量或跨模型能力。网站功能检查、合成测试通过、人工一致率与真实模型正式评分分别记录，不相互替代。
