# LoreGuard 产品文案规范

面向第一次使用的小说作者与剧情策划。页面首先说明“这是什么、我该做什么、做完会发生什么”，不要要求用户先理解实现原理。

## 默认界面只放有用的信息

- 用项目名称、文稿名称与版本、审查时间、列表记录序号帮助识别内容。不把项目、审查、案例等内部 ID、UUID、hash 或英文状态码作为标题和主信息。
- ID、内容校验值和原始方向代码保留在默认关闭的“排错信息”中。链接、请求、数据结构、React key 及测试定位仍使用原始标识，不能为了阅读体验损坏可追溯性。
- 不把长串转移到 `title` 悬浮或 `aria-label` 里；屏幕阅读器也应听到人能理解的名称。折叠后由用户主动查看完整排错坐标。
- 证据的文稿名、版本、原文摘录和行号是作者核对所必需的信息，不能当成杂项删除。故事范围会影响判断，也必须能查看，不能把未知范围默认为主线。

## 按钮说清动作和结果

| 避免 | 使用 |
| --- | --- |
| 校验并下载锁定 JSON | 完成任务并下载结果 |
| 导出 Markdown 报告 | 下载审查报告 |
| 最小连接测试 | 检查模型能否正常回复 |
| 提交、确认（没有对象） | 保存模型配置、确认两种说法的关系 |

- 下载只代表文件下载到本机，不声称已提交、上传或发送给负责人。需要自行发送时明确说明。
- 涉及模型调用，说明可能产生费用、发送哪些内容；不能把“配置已保存”写成“模型已可用”，也不能把“连接检查通过”写成“审查质量通过”。
- 错误信息说明后果与下一步；原始 HTTP、Provider、selector 等实现信息不应成为普通用户唯一能看到的解释。必要诊断可折叠保留，不删除安全和故障证据。

## 复杂判断要解释，不要改坏含义

- “作者轴”对用户称“比较标准”；“正向命题”称“用来比较的说法”或“比较句”。
- 比较句只是比较坐标，不等于正式人设，不代表角色确实做过，不代表行为好坏。实际设定以作者确认的资料与原文为准。
- 模型标签与比较句可能同向，也可能反向。审核必须保留模型标签、模型判断和比较句这三项依据，再解释“若标签成立，比较句是否也成立”。不能把同向/反向选项伪装成简单的正确/错误。
- “确认关系”不等于验证新稿事实，也不等于确认冲突。正式问题、待复核线索、材料不足必须保持区别。
- 不把推断写成已证实事实，不把一次反向行为直接等同于角色 OOC。简化用词不能省掉作者需要承担的判断。

## 新页面检查

每次修改常用页面，用第一次接触产品的人的视角检查：能否仅凭页面知道下一步；默认内容是否混入内部编号；按钮是否兑现名称；错误后是否知道如何继续。技术配置页可保留 API Key、Base URL 等服务商实际使用的字段名，但须配有简短解释。仅改变展示层时，接口、权限、版本约束与证据定位不得变化。
