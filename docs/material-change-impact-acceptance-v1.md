| 作者任务 | 本轮新增可见验收 | 复用证据或自动化 |

| 查阅变化所关联的依据 | 展示明确引用关系，不声称所有语义影响已找全；没有直接引用不等于没有影响 | `reportEvidenceReader.spec.ts` 的冻结版本、旧特征来源、多侧阅读与损坏快照边界 |
| 继续阅读和处理旧报告 | 更新后原报告、证据全文、人工反馈与未提交备注不被当前资料覆盖；已确认特征仍独立有效 | 已有原文 reader、反馈及 `test_character_trait_comparison_snapshot.py` 的来源快照规则 |
| 从提示进入复检准备 | 显示当前目标与依据，遵循服务器与 POST 共用的选材签名；读取提示、进入准备、返回都不创建分析；收费分析只在明确确认后发起 | `tests/test_revision_comparison.py` 的材料准入、幂等、权限、保守比较；现有 `RevisionReview` 与只读 `revision-browser-smoke.mjs` |
| 遇到缺失或读取失败 | 明确未知、部分数据、分页和重试；不能把失败当作没有影响或“已修复”；跨账户不可读 | 后端专项负责权限／快照／边界；集中浏览器只验证用户可见状态和恢复 |

`recheck.inputs_changed`／`can_prepare` 只说明当前材料是否可准备复检，不是语义影响、可比较性或模型质量证书。`sources` 与 `affected_issues` 的独立分页须各自处理，不从当前一页推断全量零影响。

## 一次集中验证

1. 后端／前端各自完成相关自动化与必要生产构建后，按最终 DTO 一次审查来源关系、权限、分页、选材一致性和费用触发边界。已有专项不重复全跑。
2. 集中浏览器执行本轮新增路径和确实受影响的既有阅读／复检／反馈路径；使用最终受测资源。首轮问题一次汇总给原负责人，修复后只复核受影响项，完整回归由最终官方 CI 承担。
3. 真实后端验证采用既有公开合成 QA 数据库的独立副本、普通账户 API 和真实历史报告。原 QA 数据库、旧报告与确认记录不写入；不接触用户真实项目或人工封闭题。账号临时登录材料仅在内存传递，不进入日志、截图或公共仓库。
4. 真实后端只走一个普通旅程：复用已有开航报告的“设定 v1＋草稿＋旧报告”，在副本内用正常 API 更新设定为 v2，查看变化提示，进入复检准备，再确认旧 reader 仍读 v1。具体操作与正文变体在接口稳定后固定私有 manifest，不按结果更改；这是旧真实结果的 UI／版本验证，不是本阶段新模型成绩。旧冻结 reader、反馈和确认值只做小范围前后对照，不扫描历史全库。
5. 只进入复检准备，不点击收费提交；保存实际请求方法与路径、旧／当前版本和摘要、reader 状态、无新增 AnalysisRun／模型请求的证据。明确发起新分析的产品契约由受控集成覆盖，不为该只读能力调用真实模型。
6. 额外浏览器边界只保留未纳入草稿、身份变化、无变化、加载失败与跨项目切换；后端已验证的组合不在浏览器全排列，分页只有实际交互需要才覆盖。窄屏复用同一主旅程。一套关键页截图覆盖资料变化、报告引用提示和复检准备，模拟 fixture 的边界证据与真实旧报告阅读证据分别标记。

若实际业务改动越过版本关系与交互、涉及模型调用或判断链路，先报告范围变化，由 root 决定必要验证；不自行新增模型批次。

## 条件工作量与结束条件

作者验收／集成交付预计 **4–7 小时**：准备约 0.5–1 小时，稳定版集中审查／浏览器及真实后端路径约 2–3 小时，合并修复后的受影响复核约 0.5–1 小时，CI 跟进和交付约 1–2 小时。此为条件估算，不是实际计量；不含前后端自有专项与构建，CI／外部等待也不转写为劳动工时。

结束时作者应能解释“报告用了哪版、现在什么变了、哪些结果有明确引用关联、哪些仍未知”，并主动进入现有复检准备。保留旧原文、作者决定及确认特征。完成这些任务不代表新增语义影响全覆盖，也不改变既有模型质量结论。
