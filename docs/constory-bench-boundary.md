# LoreGuard 与 ConStory-Bench 的边界

## 结论

LoreGuard 没有使用 ConStory-Bench 的代码架构，也没有导入它的数据。80 条显式指令规则回归与 100 条合成自然中文案例均由 LoreGuard 自有固定模板生成；后者明确标注为非人工标注。ConStory-Bench 仅作为相关研究和未来外部评测参考。

## 两者解决的问题不同

| 维度 | ConStory-Bench | LoreGuard |
|---|---|---|
| 目标 | 衡量不同 LLM 生成长篇故事时的一致性能力 | 帮助编剧团队在创作过程中发现、确认和修复矛盾 |
| 主要用户 | 研究者、模型开发者 | 游戏编剧、叙事设计师、内容工具工程师 |
| 输入 | 批量提示词和模型生成故事 | 项目内世界观、角色设定、章节及其版本 |
| 核心流程 | 生成 → LLM Judge → 指标 → 排行榜/分析 | 导入 → 状态抽取 → 检查 → 原文证据 → 人工反馈 → 修订 |
| 输出 | 模型级错误统计、CED/GRR、相关性和位置分析 | 可定位到文档行的具体问题、严重度、建议和处理状态 |
| 状态管理 | 以离线数据集和评测文件为主 | 项目、文档版本、任务事件、问题、反馈和恢复 |
| 当前依赖 | OpenAI-compatible 模型 Judge | 无 Key 可运行的确定性基线；模型层为可替换增强项 |

## 避免“抄袭感”的工程原则

1. 不复制 ConStory-Checker Prompt、代码、目录结构或界面。
2. 不把其五大类标签原样作为产品信息架构；LoreGuard 按可执行状态约束组织：事实、时空、知识、物品和世界规则。
3. 公开说明相关工作和许可证；若未来导入其 MIT 数据或代码，单独记录来源、版本、用途和修改。
4. 独立维护原创测试集，并把 ConStory-Bench 只作为“外部迁移评测”，不混入调参集。
5. 产品特色以工作流证据体现：文档版本、SSE 任务、证据跨度、人工反馈、状态对比和团队协作，而不是仅声称“用了 RAG/Agent”。
