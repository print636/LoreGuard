# Issue Review v1

这是 LoreGuard 的原创中文“小型规则问题证据复核集”。它用于验证一个很窄的能力：规则引擎已经给出候选问题后，AI 是否会只依据当前片段与 RAG 返回的、版本和项目均获授权的证据，给出以下三种复核结论之一：

- `supports_issue`：证据足以支持候选问题。
- `contextual_exception`：表面冲突可由规则例外、身份别名、梦境/回忆或互斥分支解释。
- `insufficient_evidence`：现有证据不足，不能把疑问、假设、传闻、缺失的另一侧事实或失效来源当成确定冲突。

## 数据边界

- 全部世界观、人物、规则、章节和标注均为本仓开发者原创，未使用商业游戏剧情，也未调用外部模型生成或修订。
- 共 12 例：`dev` 6 例、`holdout` 6 例；三个 verdict 各 4 例，并在两个 split 中各出现 2 例。
- 这是开发者可见的冻结工程测试集，不是人工盲测、开放文本能力证明或生产质量证明。
- 样本刻意覆盖跨文档时序、权限、唯一物件、身份别名、例外凭证、梦境回放、互斥剧情分支、设问/假设、缺失知识获得记录、传闻，以及旧版和错误来源隔离；不使用发色一类简单属性冲突。

## 文件约定

- `manifest.json` 保存文档元数据、证据定位、候选 issue 与期望 verdict/引用。
- `worlds/**` 是按行稳定定位的原创语料；一个非空行就是一个可引用证据单元。
- `current_evidence_ids` 是规则引擎生成候选问题时已有的片段。
- `retrievable_evidence_ids` 是允许从当前项目、当前版本检索并交给复核器的补充证据。
- `excluded_evidence_ids` 是专门用于验证版本/来源隔离的反例，不得进入模型上下文或有效引用。
- `expected.citation_evidence_ids` 是判定所需的最小黄金引用集合；实现可以返回额外的获授权证据，但不得返回伪造、过期或错误来源。

## 评测纪律

1. 只在 `dev` 上调 Prompt、阈值、检索参数和输出契约。
2. 选定配置并记录代码提交、模型标识、Prompt 版本、检索 profile、chunker 与预算后再运行 `holdout`。
3. 运行器必须先读取不含 `expected` 的执行包并原子写出预测，再由独立评分阶段加载 `manifest.json` 中的答案。
4. `holdout` 首次正式运行后不得在同一 `v1` 上重写样本或答案；如需修改，升级数据集版本。
5. 报告至少包含 verdict 准确率、三类分别准确率、期望证据覆盖率、引用 allowlist 命中率、排除证据泄漏数、失败率，以及 A/B 配置差异。
6. 对 `insufficient_evidence` 不要求模型编造缺失事实；它应明确说明缺什么，并引用能证明来源性质或缺口存在的片段。

## 推荐通过线

- 总体 verdict 至少 10/12。
- `contextual_exception` 至少 3/4，且把例外误判为 `supports_issue` 的数量为 0。
- 引用 allowlist 命中率 100%，排除证据泄漏为 0。
- 黄金证据覆盖至少 11/12。
- RAG 证据版本相较“仅当前片段”至少多答对 2 例，并在情境例外上至少多答对 2 例。

通过这些门槛只能证明“冻结小样本上的受约束证据复核”有效，不能外推到任意长篇故事或真实用户文本。
